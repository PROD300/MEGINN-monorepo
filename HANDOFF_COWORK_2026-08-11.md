## Добавление (Claude Code, та же дата) — Safari-фиксы Problem-карточек, мобильный nav, horizontal scroll Features — все замержены в main

Закрывает открытую выше задачу «MP4-фолбэк для 3D-иконок — не готово». Полная цепочка отладки в реальном Safari (iPhone, через Vercel PR-preview — ветка `preview/safari-nav-fix`, PR #1, замержен fast-forward в `main`):

- **Причина, почему иконки не отображались в Safari вообще**: Safari заявляет поддержку `video/webm`, но декод alpha-VP9 у него ненадёжен и не всегда падает обратно на MP4 `<source>` по спеке — элемент зависал на `readyState 0`. Плюс отдельный баг: `vid.currentTime = 0` выставлялся до `loadedmetadata`, что в Safari тоже может подвесить `<video>`.
- **Первая версия фикса** (детект Safari + переключение на плоский MP4-фолбэк, запечённый на тёмном фоне через `ffmpeg -c:v libvpx-vp9 ... setsar=1`) — работала статично, но давала **видимый шов на hover**: фон `.pcard` меняется на hover (`rgba(255,255,255,.03)` → `.05`), а видео несло намертво запечённый фон, не совпадающий с новым тоном.
- **Финальное решение по прямому требованию Daria — «в любом случае альфа-канал»**: HEVC+alpha недоступен (эта сборка `libx265` не поддерживает alpha-layer encoding — Apple-специфичная фича, обычно нужен macOS/AVFoundation). Вместо этого — **luma-matte техника**: пара обычных H.264-видео на каждую иконку, `<name>-rgb.mp4` (цвет) + `<name>-alpha.mp4` (маска, grayscale: белый=непрозрачно/чёрный=прозрачно), в браузере на `<canvas>` через `landing.js` (`createAlphaCanvasIcon`) сводятся в реальную поканальную прозрачность через `getImageData`/`putImageData` каждый кадр. Работает на **любом** codec-support уровне, не только в Safari. Старые плоские `obsidian-icon-*.mp4` удалены и заменены на `-rgb.mp4`/`-alpha.mp4` пары (см. `landing/assets/3D-icons/`).
- **Ещё один Safari-баг по пути**: `getImageData()` кидал `SecurityError` (tainted canvas) на видео, отданном через Range-запросы без `crossOrigin` — цикл `requestAnimationFrame` падал на первом кадре и просто останавливался навсегда (выглядело как «hover вообще не работает», карточка застывала на непрозрачном RGB-кадре с видимым швом). Фикс: `crossOrigin="anonymous"` на обоих `<video>` (сервер и так шлёт `Access-Control-Allow-Origin: *`) + `try/catch` вокруг покадровой композиции, чтобы будущий сбойный кадр не убивал цикл насовсем.
- **Touch/мобильные**: по просьбе Daria — без tap-gate, иконки автоплеятся и лупятся сами по умолчанию (`!hasHover` ветка в `landing.js`), поскольку на тачскрине hover физически недоступен.
- **Мобильный nav** (тот же PR): `.nav__mobile` был раскрыт всегда на экранах ≤720px независимо от `[hidden]` — тот же паттерн бага, что раньше был у `.form__success` (см. `HANDOFF_COWORK_2026-08-10.md`). Добавлено `.nav__mobile[hidden] { display: none; }`.

**Отдельно, другой PR (#2, ветка `preview/features-horizontal-scroll`, тоже замержен в main)** — добавлена scroll-jacked горизонтальная лента для Features-секции (S4): вертикальный скролл через «распорку» двигает `translateX` на треке карточек, пока секция запиннена (`position: sticky`). Фолбэк на обычную CSS `overflow-x` полосу на ≤900px и при `prefers-reduced-motion`. Реализация Claude Code (не second-agent), но фиксирую здесь для полноты — второй агент должен знать, что `.features-pin`/`#featuresTrack` теперь часть разметки `index.html`.

**Процесс, который использовался для обоих PR** (новый паттерн, работает в этой среде — фиксирую, т.к. второй агент может столкнуться с той же проблемой): локальный dev-сервер на `localhost` недоступен с iPhone (Windows Firewall блокирует LAN-порт, нет прав на его открытие в этой сессии). Простой пуш ветки НЕ триггерит Vercel preview в этом проекте — только Pull Request триггерит сборку надёжно. Ссылка достаётся из комментария Vercel-бота в PR (`gh api repos/.../issues/<PR#>/comments`, markdown-таблица с двумя проектами — брать `obsidian-monorepo-landing`, не `obsidian-monorepo`). Preview-деплои защищены Vercel SSO — открываются только под логином в Vercel с доступом к `obsidian-team`.
