## Новая задача в roadmap — светлая тема UI (v1.1)

Daria решила: в релиз **v1.1** добавляется разработка **светлой темы UI** — наравне с Basic Reporting и расширением на дополнительную сеть (Solana), которые уже были в этой вехе.

**Зафиксировано в:**
- `prd/prd.md` → раздел «6. Roadmap» → строка v1.1 дополнена пунктом «Light Theme UI».

**Контекст, который нужно знать перед началом работы над этой задачей:**

1. Продукт сейчас **полностью на тёмной теме по умолчанию** — переход завершён в предыдущих сессиях (`app/` и `landing/` синхронизированы, см. `ds/foundation.md` → Слой 2, `HANDOFF_COWORK_2026-08-10.md`). Светлая тема будет **новой веткой темизации**, а не откатом — тёмная остаётся дефолтом продукта, светлая добавляется как альтернативный режим.
2. В `ds/foundation.md` (Слой 2 — смысловые токены) прямо указано: разделы Surfaces/Text/Borders документируют **только текущее тёмное состояние**. Историческая светлая версия токенов (до ребрендинга 2026-08-09) была вытеснена, не архивирована отдельно — переносить один в один эти старые значения нельзя без сверки, часть примитивов и семантики с тех пор менялась (accent ramp, radius-md, функциональные цвета конвергированы в один акцент).
3. По `ds/CONTRACT.md` смена/добавление темы — это работа через **Semantic Variables**, а не точечные фиксы: нужен полный второй набор значений для семантического слоя (surface-*, text-*, border-*, bg-*), переключаемый, а не новые прибитые цвета по месту.
4. Уже был прецедент **обратного** переноса (`landing/` получил тёмную тему копированием семантики из `app/`, см. `HANDOFF_COWORK_2026-08-10.md` → «весь лендинг переведён на тёмную тему») — сейчас нужна симметричная работа: спроектировать светлый семантический слой, синхронный по структуре с тёмным, для обоих — `app/` и `landing/`.
5. Механизм переключения темы (toggle в UI, атрибут на `<html>`/`<body>`, `prefers-color-scheme` или ручной выбор пользователя) **не определён** — это отдельное архитектурное решение, нужно предложить и согласовать с Daria перед реализацией, не выбирать самостоятельно без подтверждения.

**Рекомендованный порядок работы (по существующей схеме проекта):**
1. Уточнить у Daria: light theme — переключаемая пользователем опция или просто параллельно документируемый набор токенов? Механизм переключения (toggle / системная тема)?
2. Спроектировать светлый Слой 2 (Semantic tokens) для `ds/foundation.md`, симметрично текущему тёмному — черновик на утверждение, не сразу в токены.
3. Синхронизировать с Figma (`Foundation-Tokens`, 35:2) — второй mode/набор переменных, по аналогии с текущей практикой ДС.
4. Реализовать в коде (`app/src/tokens/semantics.css`, `landing/ds/colors_and_type.css`) как переключаемый набор, не заменяя тёмный дефолт.
5. Прогнать по всем 17 экранам и лендингу, проверить контраст в обоих режимах.
6. Как обычно — **dev-превью на аппрув Daria, коммит/пуш только после «да»** (актуальная схема хэндовера, см. блок «ОБНОВЛЕНИЕ ПРОЦЕССА» в `HANDOFF_COWORK_2026-08-10.md`, продолжает действовать).

## Открытые задачи из предыдущих хэндоверов — статус

- **MP4-фолбэк для 3D-иконок Problem-карточек (Safari)** — **готово, проверено**. Второй агент положил все 3 `.mp4` рядом с `.webm` под теми же именами (`obsidian-icon-sparks/stack/tooling.mp4`), HTML их уже подхватывает без правок (`<source>`-теги в `landing/index.html` были на это рассчитаны заранее). Техническая проверка (ffprobe + сверка цвета фона): кодек h264/yuv420p с `faststart` (moov-атом в начале файла — совместимо с Safari autoplay), пропорции кадра совпадают с исходным WebM (231×458, не квадрат — hand-off про «квадратный кадр» был неточным предположением). Важно: агент отступил от буквальной инструкции в `HANDOFF_COWORK_2026-08-10.md` (там команда `ffmpeg` требовала композит на **белый** фон) и правильно скомпозировал видео на **тёмный** фон — вычисленный фон карточки `.pcard` (`rgba(255,255,255,.03)` поверх `gray-950`) даёт ≈RGB(10,13,30), фактический фон в кадре ≈RGB(8,11,29) — совпадение с точностью до квантования. Это верное решение: белый фон дал бы видимый шов на текущей тёмной карточке. Рекомендация: перед финальным коммитом всё же взглянуть глазами в самом Safari (или BrowserStack) — числовая проверка не ловит визуальные нюансы на границе (у `.pcard` есть hairline-бордер и лёгкий градиентный оверлей секции).
- **Дашборд юзер-тестов** (`dashboard/`) — заморожен по решению Daria: сервис сломан/недоступен, актуальности на данном этапе нет. Не трогать `dashboard/app/config.js` и не перегенерировать, пока не будет отдельного запроса.
