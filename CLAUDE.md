# OBSIDIAN — Project Context for Claude Code

Институциональная платформа автономного управления портфелем для Family Office CIO / Corporate Treasury Manager. B2B fintech, web, en.

**Ключевые документы:**
- `briefs/obsidian/brief.md` — продуктовый бриф v2.2
- `prd/prd.md` — PRD
- `prd/mvp_scope.md` — MVP scope

- `ia/wireframes/` — wireframe-спецификации экранов
- `ux/personas.md` — персоны (Treasury Manager, Family Office CIO, DeFi Operator)

## Как работать с проектом (оркестрация)

Рабочий процесс собран в навыки (`.claude/skills/`) — раньше это были директивы в `agents/directives/` (теперь в `_archive/`, см. `_archive/README.md`). Все навыки запускаются **только явно**, по `/имя-навыка` — сами по описанию не срабатывают (так короче и предсказуемее, чем раньше с ручными директивами).

### Маршрутизация по треку (было в `routing_rules.md`)
- **Бизнес/бриф-трек** — нет подтверждённой экранной структуры, неизвестны роли/границы, нет бизнес-метрик, слова «инициатива», «MVP», «релиз», «roadmap» → `/briefing` → `/quick-research` / `/competitive-analysis` → `/personas` → `/scope-prioritization` → `/prd-notion`.
- **UX/экраны-трек** — бизнес-контекст и роли уже зафиксированы, речь про «экран», «таблица», «dashboard», «flow», «подтверждение», «ошибка» → `/prd-to-sitemap` → `/wireframes` → `/ux-audit` → (дизайн-система: `/ds-baseline` или `/ds-scan`, затем `/grow-ui-kit` / `/component-variants`) → `/final-screens` → `/screens-audit`.
- **Дев/билд-трек** — дизайн готов, нужен рабочий продукт → `/react-base` → `/storybook` → `/screens` → `/wire` → `/handoff` → `/deploy` → `/dashboard`.
- Бизнес-трек не передаёт UX-треку задачу, пока не зафиксированы MVP, роли, critical actions и ограничения безопасности — если это не готово, веди уточнение через `/briefing` дальше, не перескакивай в экраны.

### Субагенты (`.claude/agents/`)
- **`market-researcher`** — веб-исследование конкурентов/рынка (используется внутри `/quick-research`, `/competitive-analysis`); только читает и собирает, не пишет файлы проекта.
- **`ux-heuristic-auditor`** — эвристический аудит скриншотов по Nielsen (используется внутри `/ux-audit`); только анализирует, не правит дизайн.
- Для остального (Figma/браузер-интерактив, любые правки кода/дизайна) субагентов не заводим — это держит основной агент.

### Стоячие правила (накоплены из работы с проектом)
- **Паддинги и Hug vs Stretch** — самая частая придирка при переносе Figma → код: проверяй внутренние отступы карточек и что бейджи/кнопки сидят по Hug, а не растягиваются на всю ширину, если в Figma не указано Fill.
- **Консистентность соседей** — если правишь один компонент/карточку, в финале сверь все однотипные соседние экземпляры — они должны совпадать по стилям, а не только починенный.
- **Без кодов фич в UI** — внутренние идентификаторы фичей (F01, F15, F20...) не показываются в продуктовом тексте экранов; в `.md`-документации — можно.
- **Иконки — настоящие, не плейсхолдеры** — Lucide-иконки по имени слоя/смыслу продукта, по аналогии с уже сделанными экранами.
- **Лендинг — отдельный мини-проект**, не ветка/подраздел основного прототипа.
- **План перед правками на основе внешнего фидбека** (юзабилити-тест и т.п.) — сначала короткий план, что чинишь, потом меняешь код; не лезь в длинный хвост, чини частое.
- **После изменений — живая ссылка**, не только описание в тексте: `npm run dev` и дай URL, либо задеплоенную ссылку, если просили посмотреть.
- Уточняющие вопросы — по требованию конкретного навыка (если он сам просит спросить), не как бланковая привычка на любую неопределённость.

## Дизайн-система

В проекте поставлена дизайн-система (ds_baseline, 2026-05-05). Все правила работы с интерфейсом — в `ds/CONTRACT.md`. При любых задачах, связанных с дизайном экранов, форм, компонентов:

1. Прочитай `ds/CONTRACT.md` целиком.
2. Прочитай `ds/foundation.md` и `ds/components.md` для текущего состояния токенов и UI-кита.
3. Действуй строго по правилам контракта.
